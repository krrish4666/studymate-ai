TASK: P2.1 — Fix post-generation UX state across all AI generation pages.

We are making a focused UX/state-management improvement to StudyMate AI.

The specific problem is visible in the attached screenshot:

After a result has been successfully generated, the page correctly keeps the uploaded/generated file section and the "Change file" option.

However, the generation configuration controls are STILL visible below it.

For example, on Quiz after successful generation, the page still displays:

- Difficulty
- Questions
- "Generate Quiz" button

even though the Quiz has already been successfully generated.

This makes the UI look like the generation process is still awaiting input.

WE WANT TO FIX THIS SAME UX PATTERN ACROSS THE ENTIRE APPLICATION.

==================================================
CORE UX RULE
==================================================

Every generator page must have two clearly separated UI states:

STATE 1 — BEFORE SUCCESSFUL GENERATION

Show:

- uploaded file / selected file
- configuration controls
- generation button

Example for Quiz:

File
↓
Difficulty
Questions
Generate Quiz

STATE 2 — AFTER SUCCESSFUL GENERATION

Show:

- uploaded/generated file information
- "Change file" option
- generated result
- result-specific actions if they already exist

HIDE:

- generation configuration controls
- generation button
- any UI whose only purpose is configuring a NEW generation

Example:

File
Change file

↓

Quiz result

The page should no longer visually look like it is waiting for generation.

==================================================
IMPORTANT — THIS IS A STATE CHANGE, NOT A CSS HACK
==================================================

Do NOT simply use CSS such as:

display: none

based on arbitrary selectors after generation.

The visibility of the configuration UI must be driven by the application's actual generation state.

Find the existing frontend state that determines whether generation:

- has not started
- is loading
- has succeeded
- has failed

Use that existing state wherever possible.

If the current implementation does not have a clean success-state variable, introduce the smallest appropriate frontend state needed.

Do NOT change backend APIs or generation contracts.

==================================================
CHANGE FILE BEHAVIOR
==================================================

"Change file" is IMPORTANT.

It must remain available after successful generation.

When the user chooses:

Change file

the page must return to the appropriate pre-generation state.

That means:

- current generated result should be cleared/reset according to the existing application's behavior
- new file can be selected
- generation configuration controls become visible again
- generation button becomes visible again
- the user can generate a new result

The user must NOT become trapped in the completed state.

Desired lifecycle:

                 ┌──────────────────┐
                 │  FILE SELECTED   │
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │ CONFIGURATION    │
                 │ + GENERATE       │
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │    GENERATING    │
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │     SUCCESS      │
                 │                  │
                 │ FILE              │
                 │ CHANGE FILE      │
                 │ RESULT           │
                 └────────┬─────────┘
                          │
                    Change file
                          │
                          ↓
                 ┌──────────────────┐
                 │ CONFIGURATION    │
                 │ + GENERATE       │
                 └──────────────────┘

==================================================
LOADING STATE
==================================================

Do not accidentally hide everything immediately when generation begins.

During generation:

- preserve the appropriate loading/progress UI
- prevent duplicate generation where the current application already does so
- keep the UX understandable

Only after successful completion should the page transition to the completed result state.

For Notes/Revision, respect the existing SSE lifecycle.

Do not change the SSE protocol.

Do not change:

- data:
- [DONE]
- [ERROR]
- streaming/parsing logic
- backend endpoints

Only use the existing successful completion state to transition the UI.

==================================================
ERROR STATE
==================================================

If generation fails:

DO NOT leave the page permanently in the completed state.

The user should still be able to retry.

Therefore after an error:

- generation controls should remain available or return to the appropriate generation state
- error UI should be shown using the existing application pattern
- user should be able to try again

Desired lifecycle:

Generating
    ↓
Error
    ↓
Configuration + Generate
    ↓
Retry

==================================================
IMPORTANT EDGE CASE
==================================================

Do not treat merely having an old/stale result in the DOM as proof of successful generation.

The completed state should be driven by the current generation lifecycle.

If the page is loaded with no result:

→ show generation UI.

If generation starts:

→ show loading state.

If generation succeeds:

→ hide generation UI and show result.

If generation fails:

→ return to generation UI with error state.

If Change File is selected:

→ reset result and return to generation UI.

==================================================
UI TRANSITION
==================================================

The transition between states should feel intentional.

When generation succeeds:

- configuration area can smoothly collapse/fade out
- result area can remain/appear naturally

Keep animation subtle.

Approximately:

150–250ms

Use opacity/height/transform only where appropriate.

Do NOT introduce an animation library.

Do not make the result jump unexpectedly on the page.

If animation would complicate the existing DOM/state implementation, prioritize correct state behavior over animation.

Respect:

prefers-reduced-motion: reduce

==================================================
DO NOT DUPLICATE LOGIC
==================================================

Look for the possibility of creating a small reusable frontend pattern/helper for:

- generation state
- showing/hiding generation controls
- entering completed state
- resetting on Change File

However, do NOT force a large abstraction if the existing pages have significantly different implementations.

Prefer the smallest maintainable solution.

The goal is consistency, not unnecessary refactoring.
